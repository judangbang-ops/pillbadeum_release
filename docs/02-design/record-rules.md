# 기록 규칙 (설계 초안)

이중투약 방지의 핵심 규칙임. 위젯·앱·알림 어디서 기록하든 이 문서의 규칙 하나로 판정함. 용어는 [planning-v3 용어](../01-planning/planning-v3.md#용어)를 따름.

## 1. 원칙

1. 한 창에 활성 판정(기록·건너뜀)은 최대 1개임
2. 이 보장은 DB 유니크 제약이 맡음. 앱 로직의 확인은 앞단 거름망이고, 마지막 보장은 DB임
3. 판정은 지우지 않음. 취소는 무효 처리이며 이력이 남음
4. 위젯은 비어 있는 창에만 판정을 만듦. 이미 있는 판정은 앱에서만 바꿈
5. 모든 쓰기는 공통 기록 함수 하나를 거침

## 2. 창 계산

`T0` = 하루 시작 시각(기본 04:00), `Z` = 기준 시간대(기본 Asia/Seoul). 모든 시각 계산은 `Z` 기준임.

| 주기 | 창 [시작, 끝) | 기간키 | 단계 |
| --- | --- | --- | --- |
| 매일 1회 | [D `T0`, D+1 `T0`) | `D` | MVP |
| 주 1회 (기준 요일 W) | [가장 최근 W `T0`, +7일) | 창 시작 날짜 | MVP |
| N일마다·격주 | 기준일부터 N일 간격 | 창 시작 날짜 | 확장 |
| 하루 N회 | 하루 창을 슬롯으로 나눔 | `D#slot` (예: `2026-11-11#evening`) | 확장 |
| 주 N회 | 주 창을 슬롯으로 나눔 (예: 월·목) | `W#slot` | 확장 |
| 필요시(PRN) | 창 없음 | 기간 멱등 대상 아님 | 확장 |

예시 (`T0` = 04:00):

| 실제 시각 | 주기 | 창 | 기간키 |
| --- | --- | --- | --- |
| 2026-11-11 08:02 | 매일 | 11-11 04:00 ~ 11-12 04:00 | `2026-11-11` |
| 2026-11-12 00:30 | 매일 | 11-11 04:00 ~ 11-12 04:00 | `2026-11-11` |
| 2026-11-15(일) 22:00 | 주 1회(월) | 11-09 04:00 ~ 11-16 04:00 | `2026-11-09` |
| 2026-11-16(월) 08:00 | 주 1회(월) | 11-16 04:00 ~ 11-23 04:00 | `2026-11-16` |

규칙

- 필요시(PRN) 약은 "같은 창이면 한 번"이 성립하지 않음. 최소 간격과 하루 최대 횟수로 따로 보호함
- 주 N회를 "한 주에 N번까지 기록"으로 만들면 연타 두 번이 두 회차로 들어감. 반드시 슬롯 창으로 나눔

## 3. 기간키

- 형식: 창 시작 날짜 `YYYY-MM-DD`, 슬롯이 있으면 `#slot`을 붙임
- 쓰지 않는 것
  - **상대 회차 번호** (기준일부터 0, 1, 2…): 기준일을 옮기면 새 버전의 회차 번호가 옛 버전과 겹쳐 실제 투약이 "이미 기록됨"으로 버려짐 ([실증 T11](../06-review/review-v2.md#실증-결과))
  - **ISO 주번호** (`2026-W46`): 연도 표기를 잘못 섞으면 같은 주가 연말연초에 키 2개로 갈라짐. 2026년은 53주가 있는 해라 이번 연말에 바로 해당함 (실증 T8)

## 4. 저장 구조

기록 행(`dose_record`)의 주요 열은 다음과 같음. 전체 정의는 [data-model](data-model.md#dose_record-판정)에 있음.

| 열 | 뜻 |
| --- | --- |
| `intake_id` | 복용 항목 |
| `period_key` | 이 판정이 채우는 창의 기간키 |
| `kind` | `TAKEN`(복용) / `SKIPPED`(건너뜀) |
| `taken_at` | 실제 복용(또는 건너뜀 결정) 시각, UTC epoch ms |
| `zone_id` | 그때의 기기 시간대 |
| `recorded_at` | 입력한 시각 |
| `source` | `WIDGET` / `APP` / `NOTIFICATION` |
| `active` | 활성이면 1, 무효면 NULL |
| `voided_at`, `void_reason` | 무효 처리 시각·사유 |

유니크 제약: `UNIQUE(intake_id, period_key, active)`

- SQLite는 유니크 비교에서 NULL끼리 서로 다르다고 봄. 그래서 무효 행(`active` = NULL)은 몇 개든 남고, 활성 행(`active` = 1)은 창마다 1개만 들어감
- 부분 인덱스(`WHERE voided_at IS NULL`)도 같은 효과지만 Room의 `@Index`로는 선언할 수 없어 이 방식을 씀
- 순수 이벤트 로그(취소도 새 행) + `UNIQUE(항목, 기간키)`는 쓰지 않음. 취소 이벤트 자체가 안 들어가거나, 취소 후 재기록이 막힘 (실증 T1)

## 5. 판정 계산

창 W(시작, 끝, 기간키)에 대한 활성 판정은 다음 조건으로 찾음.

```sql
SELECT * FROM dose_record
WHERE intake_id = :intakeId
  AND active = 1
  AND (period_key = :periodKey
       OR (taken_at >= :windowStart AND taken_at < :windowEnd))
ORDER BY taken_at
LIMIT 1;
```

- `taken_at`이 창 안에 있는지 함께 보는 이유: 주기·기준일·하루 시작 시각이 바뀌면 같은 창이라도 기간키 모양이 달라짐. 키만 비교하면 "매일 → 주 1회"로 바꾼 날 같은 약이 두 번 기록됨 (실증 T9)
- `period_key`를 함께 보는 이유: 조기 투약을 "다음 회차 몫"으로 기록하면 복용 시각은 이번 창 안이지만 기간키는 다음 창임
- 인덱스: `(intake_id, taken_at)`, `(intake_id, period_key, active)`

## 6. 쓰기 절차

공통 기록 함수 `RecordDose` 하나가 위젯·앱·알림의 모든 기록을 처리함. 아래는 Room 3 기준 의사 코드임.

```kotlin
suspend fun recordDose(cmd: RecordCommand): RecordResult =
    db.useWriterConnection { conn ->
        conn.immediateTransaction {
            val intake = intakeDao.find(cmd.intakeId)
            if (intake == null || intake.archivedAt != null) return@immediateTransaction RecordResult.Gone

            val window = windowOf(intake, cmd.now, settings)        // 기준 시간대 + 하루 시작 시각
            if (cmd.renderedPeriodKey != null && cmd.renderedPeriodKey != window.periodKey)
                return@immediateTransaction RecordResult.Stale(window.periodKey)

            doseDao.activeIn(intake.id, window)?.let { return@immediateTransaction RecordResult.Already(it) }

            val rowId = doseDao.insertOrIgnore(DoseRecord.taken(intake.id, window.periodKey, cmd))
            if (rowId == -1L) {
                // 0행 삽입이 곧 중복이라는 뜻은 아님 (OR IGNORE는 NOT NULL 위반도 조용히 넘김)
                val existing = doseDao.activeIn(intake.id, window)
                    ?: return@immediateTransaction RecordResult.Error("insert ignored without active row")
                return@immediateTransaction RecordResult.Already(existing)
            }
            RecordResult.Recorded(rowId)
        }
    }.also { result -> afterWrite(result) }   // 위젯 전체 갱신 + 그 창의 남은 알림 취소
```

| 결과 | 위젯·알림 안내 |
| --- | --- |
| `Recorded` | 완료 표시 + 기록 시각 |
| `Already` | "이미 기록됨 (08:02). 변경 없음" |
| `Stale` | 기록하지 않고 새로고침 + "날짜가 바뀌었어요. 다시 눌러 주세요" |
| `Gone` | 기록하지 않고 새로고침 (보관·삭제된 항목) |
| `Error` | 오류로 남김. 중복으로 숨기지 않음 |

### 6.1 무효 처리 (취소, 앱 전용)

```sql
UPDATE dose_record
SET active = NULL, voided_at = :now, void_reason = :reason
WHERE id = :id AND active = 1;
```

- 확인 절차를 거친 뒤 실행함
- 창이 아직 열려 있으면 그 창의 반복 알림을 다시 계산함

### 6.2 건너뜀

- `kind = SKIPPED`로 `RecordDose`와 같은 절차를 밟음. 위젯에는 건너뜀 버튼이 없음 (앱·알림에서만)

### 6.3 판정 바꾸기 (앱 전용)

- 예: 건너뜀 → 복용. 한 트랜잭션 안에서 기존 판정을 무효 처리하고 새 판정을 삽입함

### 6.4 실제 복용 시각 수정 (앱 전용)

- `taken_at`을 고치면 기간키도 새 시각의 창으로 다시 계산함 (조기 투약으로 지정한 경우는 제외)
- 옮겨 갈 창에 이미 활성 판정이 있으면 저장하지 않고 사용자에게 알림

## 7. 대조 규칙

- **렌더 기간키 대조**: 위젯 버튼과 알림 버튼은 자신이 만들어질 때의 기간키를 함께 보냄. 지금 기간키와 다르면 기록하지 않음
  - 이유: 날짜가 바뀐 뒤 갱신이 늦은 위젯의 완료 칸을 "확인하려고" 누르면, 대조가 없을 때 오늘 몫이 거짓으로 기록되고 실제 복용은 빠짐 (실증 T10)
- **보관 항목 대조**: 버튼의 항목이 보관됐으면 기록하지 않음
- **위젯 머리글 날짜**: 위젯이 어느 날 기준으로 그려졌는지 보여줌. 갱신이 늦어도 사용자가 알아봄

## 8. 시간·일정 변경

| 상황 | 동작 |
| --- | --- |
| 기기 시간대 변경 | 창은 기준 시간대로 계산하므로 바뀌지 않음. 표시 시각만 기기 시간대로 보여줌 |
| 기준 시간대 설정 변경 | 바꾼 시점부터 적용함. 과거 기록의 기간키는 바꾸지 않음 |
| 하루 시작 시각 변경 | 바꾼 시점부터 적용함. 판정은 창 안의 복용 시각으로도 보므로 같은 날 중복이 생기지 않음 |
| 시계를 미래로 돌림 | 미래 시각 기록이 생기면 앱에서 경고를 보여줌. 판단은 사용자가 함 |
| 주기 변경 (예: 매일 → 주 1회) | 새 일정 버전을 만듦. 새 창 안에 기존 기록이 있으면 완료로 판정함 |
| 주 1회 늦은 투약 | 그 창에 기록함. 약별 설정(매번 묻기·항상 옮기기·항상 유지)에 따라 기준일을 옮김. 옮기면 새 버전의 창이 늦은 날부터 시작하고, 방금 기록이 그 창을 채움 |
| 주 1회 조기 투약 | 위젯은 "이미 기록됨"으로 막음. 앱에서 "다음 회차 몫으로 기록"을 고르면 `period_key`를 다음 창으로 지정해 저장하고, 기준일 이동 여부를 물음 |
